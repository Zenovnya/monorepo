# Движок отбора кейсов

Документ описывает **что именно** решает сервер, когда пользователь нажимает
«следующий кейс», и почему решает так. Правила перенесены из спецификации
«Лапы Закона MVP 1.0» без «улучшений»: любая правка здесь меняет то, на чём
учится человек.

- Код: `backend/app/modules/adaptive/` (`engine.py` — чистые правила,
  `service.py` — связь с БД, `pack.py` — проверка контента).
- Эталон: `backend/tests/fixtures/theme_engine_reference.py` — исходный код из
  спецификации, по которому сверяется наш порт.
- Сверка: `backend/tests/test_adaptive_engine.py` прогоняет одни и те же
  случайные сценарии через оба движка; расхождение валит тест с номером
  сценария и шагом.

## Что сервер считает и чего не считает

| Считает сервер | Не считает сервер |
|---|---|
| Какой кейс показать и какой не показать | Правильность «по смыслу» ответа |
| Совпал ли `option_id` с ключом | Свободный текст ответа |
| Окно наблюдений и приоритет темы | «Уровень знаний» и проценты правоты |
| Засчитывать ли попытку и почему нет | Оценку старания или скорости |

Смысл разделения: оценка должна быть **проверяемой**. Пока вердикт выносит
сверка с ключом, любой ответ можно перепроверить по журналу. Если бы вердикт
выносила языковая модель, проверить его было бы нечем.

## Окно и приоритет темы

Для каждой темы берутся **последние пять** засчитанных наблюдений; отозванные
(`voided`) исключаются до среза окна — иначе карантин одной ошибки сдвинул бы
окно и «простил» её.

```
need     = (2 + errors) / (4 + n)
priority = need × weight_pct / 100
```

- `n` — сколько ответов в окне (0–5), `errors` — сколько из них неверных.
- Сглаживание `2/4` — холодный старт: тема без наблюдений даёт 50%, а не 0% и
  не 100%. Это **приоритет полезной практики**, а не вероятность знания.
- `weight_pct` — редакционные веса тем (80–120% с шагом 5); по умолчанию 100.
- Считается точной дробью (`Fraction`), в ответ API уходит float. Округление
  безопасно: ранжирование уже произошло.

Метки состояния: `NOT_ASSESSED` (n = 0), `LIMITED` (n ≤ 2), `RECENT_RESULTS`.

## Выбор темы

Кандидаты — темы, у которых есть **свежий** кейс: `recommend_case`, которого
пользователь ещё не видел (семья заданий не встречалась).

Порядок выбора минимального элемента:

1. `-priority` — выше приоритет, раньше тема;
2. `n != 0` — непроверенная тема раньше проверенной при равном приоритете;
3. `last_auto_seq` — тема, которую давно не выдавали автоматически;
4. `order` темы — порядок из пака;
5. `topic_id` — для полной воспроизводимости.

При пустом профиле все темы равны, и первым идёт `CIV01_R1`. Это не «случайный
выбор», а следствие правила — и проверяется тестом.

### Ротация

Если две последние автоматические выдачи пришлись на одну тему, третью по ней
не выдаём: среди остальных сначала берутся темы без наблюдений
(`reason = ROTATE_TOPIC`). Считаются **выдачи**, а не ответы: пропуск серию не
сбрасывает.

### Внутри темы

Сначала подтег (`subtopic_id`), по которому последний ответ в окне был
ошибкой — поле `matched_error_tag`. Затем `lesson.order`, затем `item.id`.

## Режимы и зачёт

| Режим | Где | Засчитывается |
|---|---|---|
| `fresh_case` | `recommend_case` через `/next` | Да, если семья новая |
| `check` | `lesson_check` из урока | Да, если семья новая |
| `practice` | повтор, `preexposed` | Нет |
| `guide` | разбор урока | Нет (это не проверка) |

Порядок причин незачёта — **он важен**, потому что объяснения разные:

```
SKIP → REVEAL → NOT_ASSESSMENT → FAMILY_SEEN → PRACTICE → ASSISTED → COUNTED
```

- `SKIP`/`REVEAL` — пользователь сам отказался отвечать;
- `NOT_ASSESSMENT` — учебный разбор;
- `FAMILY_SEEN` — по этой семье заданий уже был засчитанный ответ;
- `PRACTICE` — тренировка;
- `ASSISTED` — была подсказка;
- `COUNTED` — засчитано.

`help` попытку **не закрывает**, но `assisted=True` остаётся навсегда: ответ
после подсказки засчитан не будет.

Повторное действие по закрытой попытке возвращает `already_closed: true` и не
меняет исход. Две вкладки с разными ответами: выигрывает первая.

## Что запрещено клиенту

- Назначить `mode`/`origin` самому: `origin=auto` допустим только с
  `fresh_case`, и ручка принимает его только из `/next`.
- Открыть вторую попытку: `OPEN_ATTEMPT`, в БД блокировка строки состояния.
- Получить ключ до ответа: карточка содержит только `{id, text}`.
- Ответить за другого пользователя: чужая попытка — `UNKNOWN_ATTEMPT` (404).

## Состояние и воспроизводимость

`seq` монотонен на пользователя и заменяет время в сортировке: два ответа в
одну секунду не должны менять приоритет. `created_at` остаётся только для
аудита.

```sql
adaptive_states            -- seq, открытая попытка, веса тем, ключ релиза
adaptive_attempts          -- выданные карточки и исход
adaptive_observations      -- засчитанные ответы (voided вместо удаления)
adaptive_seen_families     -- показанные семьи заданий
adaptive_topic_priorities  -- снимок приоритетов для экрана прогресса
```

Одинаковое состояние даёт одинаковый ответ — это проверяется тестом на
случайных сценариях. Поэтому при споре «почему мне показали это» можно
восстановить цепочку по журналу.

## Карантин наблюдения

`void_observation(attempt_id)` ставит `voided = True`, не удаляя запись: нужно
видеть, что ответ был, но чтобы окно его не учитывало. История не
переписывается.
