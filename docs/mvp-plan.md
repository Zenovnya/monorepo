# План до MVP

Актуально на 31.10.2026. Основано на аудите репозитория и приоритетах продукта.

## Принцип

В коде уже есть большой функциональный фундамент. Задача — не добавлять новых
фич, а довести существующее до состояния продукта: один цельный учебный
сценарий, достаточный объём связанного контента, единый визуальный язык.
Платежи, push и OAuth до закрытой беты не нужны — но недействующие обещания
(premium без оплаты, кнопки-заглушки) нужно убирать.

## Этап 1 — единый контентный механизм

Проблема: два параллельных пайплайна контента.

1. Legacy: `units` -> `lexbear_lessons` -> `questions` / `theory_cards`, и `cases` /
   `case_options`. Питает `/lexbear/*` и экраны «Учёба» / «Кейсы».
2. Адаптивный: `learning_cases` -> `learning_case_versions` -> `learning_case_steps`
   -> `learning_case_answers` + `learning_competencies`. Питает `/learning/*`.

`app/content_packs/cases.json` содержит 100 кейсов, но в адаптивный банк попадал
только один кейс из `app/modules/learning/seed.py`, поэтому `GET /learning/next`
фактически выбирал из одной позиции.

Решение: адаптивный банк — единственный контентный механизм для отбора кейсов,
legacy-таблицы наполняются из тех же паков для обратной совместимости API.

- `POST /admin/content/reload-adaptive` — идемпотентный импорт `cases.json`
  в адаптивный банк (ключ — `slug` -> `CaseVersion.source_slug`).
- `GET /admin/content/adaptive/review` — очередь юридической проверки.
- `POST /admin/content/adaptive/review/{slug}` — статус `in_review` / `approved`.
- `python -m app.seed` теперь создаёт стартовый кейс и сразу импортирует паки.

Важно: импорт != юридическая проверка. `review_status` по умолчанию `imported`,
`approved` выставляется отдельно и фиксирует проверяющего и время.

## Этап 2 — Visual Identity & Motion System

См. `docs/design/visual-audit.md` — аудит 18 экранов, дизайн-токены, motion-правила.

Сделано в рамках этапа:

- `mobile/src/theme/tokens.js` — единый источник визуальных значений: цвета
  (включая тинты `goldTint` / `successTint` / `errorTint`, `borderSoft`, `shadow`),
  7 ролей типографики, шкала отступов `xs..xxl`, радиусы `sm..pill`,
  глубина `press` / `card` / `floating`, высоты интерактивных элементов.
- `mobile/src/theme/colors.js` оставлен как алиас палитры для старых импортов
  (помечен `@deprecated`), чтобы переход на токены шёл без массового рефакторинга.
- `mobile/src/theme/motion.js` — длительности, кривые, spring-пресеты, каскад.
- `mobile/src/hooks/useReducedMotion.js` — подписка на системную настройку
  «уменьшить движение»; все новые анимации её учитывают.
- Motion-примитивы: `FadeInView` (каскадное появление), `AnimatedStep`
  (переход между шагами с направлением), `ProgressBar` (анимация роста).
- Системные состояния: `ErrorState` / `EmptyState` / `LoadingState` / `Skeleton`

- Пересобраны 4 ключевых экрана на токенах: онбординг, диагностика,
  экран кейса, экран прогресса. Хардкод-цвета в них заменены токенами,
  анимации добавлены, `minHeight` у пузыря маскота убран.
- `app.json`: сплэш и adaptive icon используют цвет фона `#F6F1E8` вместо
  `#ffffff`, чтобы не было белой вспышки при запуске.

## Этап 3 — доверие к серверу

`POST /lexbear/lessons/{id}/complete` больше не принимает `correct`/`total` от клиента.

- Новый контракт: `{"answers": {"<question_id>": <ответ>}}`. Ответ — число
  (одиночный выбор), список чисел (множественный выбор) или булево (true/false).
- Сервер загружает вопросы урока из БД и сам сравнивает ответы с эталоном
  (`app/modules/content/lexbear_scoring.py`). Клиент не влияет ни на
  знаменатель, ни на то, какие ответы считаются правильными.
- `total` — число вопросов в уроке, а не число присланных ответов: пропущенные
  вопросы засчитываются как неправильные, иначе можно было бы улучшить
  результат, просто не отправляя сложные вопросы.
- Множественный выбор сравнивается как множество (порядок не важен); частичный
  или избыточный набор — неверный ответ. Один битый ответ не роняет весь урок,
  он просто не засчитывается.
- Ответ теперь содержит серверные `correct` и `total` — по ним мобильный экран
  показывает итог, чтобы он совпадал с начисленным XP.
- Старый контракт (`correct`/`total` без `answers`) отвечает 422: тихо
  засчитывать «0 из N» нельзя — это обнуляло бы честно пройденный урок.

Тесты: `backend/tests/test_lesson_scoring.py` (21 тест, без БД).
Итого по этапам 0-3: 85 passed, 1 skipped.


## Этап 4 — контент

- Минимум для MVP: 25 уроков, 125 вопросов, 100 кейсов в адаптивном банке.
- Пустые юниты `koap-road` и `tk` отключены флагом `is_active: false` в паках:
  `load_content()` ставит `Unit.is_active = unit_in.is_active` (раньше всегда
  `True`), а `list_units()` фильтрует по этому полю — пустые острова больше не
  доезжают до клиента. Прогресс и FK сохраняются: это мягкое удаление.
- Приоритет — одно направление (взаимодействие с полицией), доведённое до
  полного пути: теория -> практика -> интерактивная ситуация -> разбор -> повторение.

### Сделано: флагманский юнит «Общение с полицией»

- `backend/app/modules/content/police_unit.py` — единственный источник истины
  для юнита: 25 уроков × 5 вопросов, у каждого урока 3 карточки теории.
  Генерация вместо ручного JSON: индекс правильного ответа задаётся числом
  рядом с вариантами, поэтому не «съезжает» при правке текста.
- Перезапись пака: `python -m app.modules.content.police_unit` (идемпотентно;
  второй запуск даёт `updated`, а не дубль). Команда сама валидирует юнит
  через `UnitIn` и вставляет его в `curriculum.json` с `order: 4`.
- Порядок юнитов уникален: `const` 1, `uk-property` 2, `uk-fraud` 3,
  `police` 4, `koap-road` 5, `tk` 6 (`Unit.order` напрямую сортирует список
  в `lexbear_service.list_units`, совпадающие значения дают плавающий порядок).
- Структура уроков: 1-8 базовые сценарии (основания, документы, беседа,
  задержание, досмотр, протокол, доставление, разъяснение прав), 9-13
  фиксация и обжалование (видеосъёмка, жалоба, границы силы, визит домой,
  обыск), 14-18 транспорт и процедуры (остановка авто, мероприятия, штраф,
  дактилоскопия, жалоба через Госуслуги), 19-22 общение (тон, конфликт,
  несовершеннолетний, иностранный гражданин), 23-25 надзор и итог
  (прокуратура, чек-лист, экзамен на 20 XP).
- Тесты: `backend/tests/test_police_unit.py` (10 тестов, без БД) — схема
  `UnitIn`, 25 уроков / 125 вопросов, порядок 1..25, уникальность slug,
  валидные индексы ответов, наличие теории, сверка `curriculum.json`
  с генератором (ловит забытый перезапуск генератора), флаг `is_active`
  у флагмана, выключенность пустых юнитов и уникальность `Unit.order`.
- Итого по этапам 0-4: 95 passed, 1 skipped, `ruff` чистый.

Осталось на этапе 4: юридическая проверка кейсов. В `cases.json` ровно 100
кейсов, но полей статуса проверки в паке нет — `review_status` у всех остаётся
`imported`, пока ревьюер не пройдёт их через
`POST /admin/content/adaptive/review/{slug}`.
