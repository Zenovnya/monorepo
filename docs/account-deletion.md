# Удаление аккаунта

Требование магазинов приложений: если в приложении есть регистрация, пользователь
должен иметь возможность удалить аккаунт **в самом приложении** (App Store
Review Guideline 5.1.1(v), Google Play — Account Deletion). До этой реализации
единственным управлением аккаунтом был выход из системы: почта, прогресс и
история платежей оставались на сервере навсегда.

## Сценарий

1. Настройки → «Удалить аккаунт» → подтверждение (`Alert` на iOS/Android).
2. Экран `DeleteAccountScreen`: список того, что исчезнет, галочка «понимаю» и
   ввод текущего пароля.
3. `DELETE /user/me` с телом `{ "password": "..." }`.
4. Успех → кэш React Query очищается (`queryClient.clear()`), сессия
   сбрасывается, приложение возвращается на экран входа.

Каждый шаг необратим, поэтому кнопка активна только после галочки и непустого
пароля, а сервер дополнительно проверяет пароль (403 при неверном).

## API

```
DELETE /user/me
Authorization: Bearer <access_token>
{ "password": "текущий пароль" }

200 { "deleted": true, "email": "user@example.com", "leftover_rows": 0 }
403 { "detail": "Неверный пароль" }
422 тело без пароля
```

Пароль обязателен: access-токен живёт 15 минут, и одного украденного токена для
необратимой операции недостаточно.

## Как удаляются данные

`app/modules/user/service.py::delete_account`

1. Удаляется строка пользователя. У 20 таблиц внешний ключ объявлен с
   `ON DELETE CASCADE` — прогресс, токены, подписки, достижения, уведомления,
   повторения и платёжная история уходят одним запросом. Порядок разрешает
   Postgres, а не приложение: между дочерними таблицами тоже есть связи
   (`review_logs` → `review_states`, `learning_attempts` → `learning_case_*`),
   и ручной порядок удаления рано или поздно нарушил бы FK.
2. Затем «подметаются» строки с этим `user_id` во всех моделях, у которых колонка
   `user_id` ссылается на `users.id`. Список моделей собирается по метаданным
   (`Base.registry.mappers`), а не пишется руками: иначе при добавлении новой
   таблицы её забыли бы, и персональные данные пережили бы удаление. В Postgres
   после каскада таких строк нет, и `leftover_rows` = 0 — это индикатор
   аномалии. В sqlite (тесты) каскад по умолчанию выключен, и именно второй шаг
   действительно чистит данные.

## Тесты

`backend/tests/test_user_account.py`

- валидация `DeleteAccountIn` (пароль обязателен);
- сбор моделей по метаданным: в списке есть прогресс, токены, push-таблицы,
  подписки — и нет контентных таблиц (уроки, статьи, вопросы);
- полный сценарий на sqlite: пользователь и его `daily_xp` исчезают, `email`
  возвращается в ответе;
- `TestClient`-сценарий проверен вручную: неверный пароль → 403, пустое тело →
  422, верный пароль → 200, `GET /user/me` после удаления → 404.

`backend/tests/test_autopayments.py`

- `stop_autopayments` стирает способ оплаты, выключает продление и отменяет
  `pending`-платёж;
- отказ шлюза не отменяет удаление, но и не выдаётся за успех;
- `delete_account` возвращает `had_subscription` и `autopayment_stopped` для
  сценариев «с подпиской» и «без подписки»;
- разбор webhook ЮKassa: способ оплаты берётся из `payment_method`, заказ — из
  `metadata.order_id`;
- без ключей шлюз не подтверждает отмену и не создаёт платёж.

## Автоплатежи

До недавнего времени подписка при удалении аккаунта **не отменялась**: магазин
продолжал списывать деньги по сохранённому способу оплаты, а после каскадного
удаления подписки идентификатор способа терялся — отменить платёж было нечем.

Сейчас `delete_account` первым шагом вызывает
`payments.service.stop_autopayments` (до удаления строки пользователя, иначе
способ оплаты уже не найти):

1. Берёт `subscriptions.payment_method_id`; если подписка оформлена до миграции
   `0024`, спрашивает список сохранённых способов у шлюза.
2. Отменяет все платежи в статусе `pending` (`POST /v3/payments/{id}/cancel`) —
   платёж, созданный за минуту до удаления, иначе прошёл бы уже после.
3. Обнуляет `payment_method_id`, выключает `auto_renew`, помечает подписку
   `canceled`.

Важно про ЮKassa: **API удаления сохранённого способа оплаты у неё нет**. По
документации отключение автосписаний — это прекращение использования
идентификатора на стороне магазина, то есть удаление его из своей базы. Именно
это и делает `stop_autopayments`; вызова «revoke» в API не существует, поэтому
его нет и в коде.

Если шлюз недоступен, удаление аккаунта всё равно проходит (это требование
магазинов и не должно зависеть от платёжного провайдера), но ответ содержит
`autopayment_stopped: false`, а приложение показывает на экране входа
предупреждение: «автоплатёж не отменён, свяжитесь с поддержкой». Молчать об этом
нельзя — это деньги пользователя.

Ответ `DELETE /user/me`:

```json
{
  "deleted": true,
  "email": "user@example.com",
  "leftover_rows": 0,
  "had_subscription": true,
  "autopayment_stopped": true,
  "canceled_payments": 1
}
```

## Что стоит учесть в проде

- Письмо с подтверждением удаления не отправляется (осознанно: письмо содержит
  адрес уже удалённого пользователя, а канал `email_service` рассчитан на
  сброс пароля).
- Уже **успешные** платежи не возвращаются автоматически: удаление аккаунта
  отменяет будущие автосписания, а возврат за прошедший период — отдельная
  операция поддержки (в ЮKassa это `POST /v3/refunds`).
