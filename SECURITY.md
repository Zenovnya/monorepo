# Безопасность

## Как сообщить об уязвимости

Не открывай публичный issue. Напиши на адрес команды (владелец репозитория)
с описанием: что за уязвимость, как воспроизвести, что может сделать
злоумышленник. Мы отвечаем в течение 3 рабочих дней и сообщим, когда будет
исправление; публично раскрываем проблему только после фикса.

Отдельно — **ошибки в правовом контенте**: они для нас приоритетнее
продуктовых задач, потому что цена неверной нормы — действия пользователя в
реальной ситуации. См. `docs/legal-content-policy.md`, раздел «Ошибки в
опубликованном контенте».

## Что уже сделано

### Аутентификация и сессии

- Пароли — **bcrypt**; проверка вынесена в `verify_password_async`, чтобы
  не блокировать event loop.
- Access-токен — JWT (`HS256`), живёт 60 минут; refresh — 30 дней.
- **Refresh-токены хранятся как sha256-хеш** (`refresh_tokens.token`): дамп
  базы не даёт войти по чужому токену.
- Сброс пароля: в БД только **хеш** токена, `used_at` делает его одноразовым,
  новый запрос инвалидирует предыдущие ссылки, успешный сброс **отзывает все
  refresh-токены** пользователя.
- `POST /auth/forgot-password` отвечает одинаково для существующего и
  несуществующего email — иначе это проверялка зарегистрированных адресов.
- `JWT_SECRET_KEY` короче 32 символов при `DEBUG=false` не даёт приложению
  стартовать: слабый секрет — не «настройка по умолчанию», а отказ.

### Доступ и лимиты

- Всё, что требует пользователя, получает `uuid` из токена и **не принимает
  user_id из тела запроса** — иначе достаточно подставить чужой id.
- При повторном ответе на диагностический кейс возвращается уже сохранённая
  попытка, а не создаётся новая (идемпотентность + защита от накрутки).
- Админские эндпоинты (`/admin/*`, `/lexbear/seed`) требуют
  `X-Admin-Token`; без токена в production они недоступны.
- Глобальный rate limit по IP (`RATE_LIMIT_MAX` / `RATE_LIMIT_WINDOW`),
  состояние в Redis, откат в память процесса при его недоступности.
  Жёсткие лимиты: `forgot-password` — 3 / 5 мин, `reset-password` — 10 / 5 мин.
- `X-Forwarded-For` читается только при `TRUST_PROXY_HEADERS=true`, и берётся
  **правый** элемент: при прямом доступе заголовок подделывается, и лимит
  обходился бы сменой строки.
- Смена статуса юридической проверки фиксирует `reviewed_by` и `reviewed_at`;
  непроверенный кейс не показывается пользователю (гейт в
  `learning/service.py`).

### CORS

Allowlist `CORS_ORIGINS` плюс опциональный `CORS_ORIGIN_REGEX` (только для
LAN-адресов Expo в разработке). В production regex оставляют пустым.
Заголовки CORS выставляются и на ответах об ошибках, которые формируются в
middleware: иначе клиент видел бы «Network Error» вместо причины.

### Данные

- Публичная OpenAPI-схема и `/docs` **выключены** при `DEBUG=false`:
  в проде структура API не раскрывается.
- `response_model` отсекает случайную утечку полей (например,
  `hashed_password`) даже если модель выросла.
- Удаление аккаунта: пароль обязателен (`403` при неверном), автоплатежи
  отключаются до удаления строк, данные уходят каскадом плюс «подметание» по
  метаданным моделей.
- В логи не попадают токены; ошибки Resend/Expo/шлюза логируются без тела
  запроса с секретами.

### Входящие webhook и внешние интеграции

- Webhook платёжного шлюза проверяет подпись (HMAC-SHA256) и **без секрета
  отклоняется в production** (`503`), а не принимается «на веру».
- Начисления идемпотентны по `payment_history.status`: повторная доставка
  webhook не начисляет гемы дважды.
- Токены push-устройств, на которые Expo ответил `DeviceNotRegistered`,
  гасятся (`is_active = false`).

## Что стоит знать

- **CI не имеет доступа к прод-секретам**: тесты используют фиктивный
  `JWT_SECRET_KEY` и sqlite. Значения из `.env` в репозиторий не попадают.
- **Python-зависимости проверяются `pip-audit`** в workflow `security.yml`
  (`--ignore-vuln PYSEC-2026-1325`: уязвимость в `ecdsa`, исправленной версии
  пока нет). Для JS зависимости `package-lock.json` фиксируется, но
  автоматического `npm audit` в CI нет — это известный пробел.
- **Секреты — только в окружении**: `JWT_SECRET_KEY`, `ADMIN_TOKEN`,
  `RESEND_API_KEY`, `YOOKASSA_SHOP_ID`/`YOOKASSA_SECRET_KEY`,
  `PAYMENTS_WEBHOOK_SECRET`, `SENTRY_DSN`. В коде и в `.env.example` только
  пустые значения.

## Известные ограничения

- **Запросы на возврат средств** не автоматизированы: удаление аккаунта
  отменяет будущие автосписания, но уже прошедшие платежи возвращаются
  вручную.
- **Нет 2FA** и входа через сторонние провайдеры (`SocialButton` в интерфейсе
  пока не подключён к реальному OAuth).
- **Rate limit по IP**, а не по пользователю: за общим NAT лимит делится на
  всех. Для MVP приемлемо, при росте — лимит по `user_id` поверх IP.
- **Нет WAF/бот-защиты**: спам-регистрации ограничены только лимитом частоты.
